Start here / 0-5 minutes

Clarify what "unique" means

"Do we need standard UUIDs or any unique identifier? Must IDs be 64-bit, time-sortable, or unpredictable? Are gaps acceptable? What throughput and failure guarantees do we need?"

Functional requirements

RequirementExpected behavior
Generate an IDProvide an API that returns one new ID per successful request.
Global uniquenessNever repeat an ID across generators within the supported lifetime, under the stated ownership, clock, and recovery rules.
Compact representationUse a 64-bit ID, returned as a decimal string to preserve precision in clients.
Approximate time orderingIDs should generally sort by creation time; strict global ordering is not required.
Batch generation (optional)Return a bounded number of unique IDs in one request if the interviewer includes batching in scope.

Non-functional requirements

RequirementDesign expectation
High throughputSupport an illustrative 1 million IDs/second globally; at 100 workers, average load is about 10,000 IDs/second each before headroom and skew.
Low latencyKeep normal generation local to the worker; agree on an end-to-end p99 latency target with the interviewer.
Horizontal scalabilityAdd independently identified workers within the worker-ID bit budget, without central coordination for every ID.
AvailabilityContinue through healthy generators when a worker fails; stop any generator whose ownership or time safety is uncertain.
Safe recoveryHandle restarts and clock rollback without reusing previously issued timestamp-worker-sequence combinations.

Out of scope: gapless numbering, strict global ordering, secret/unpredictable tokens, and storing all generated IDs. Gaps are acceptable.

First decision: if 128-bit IDs are acceptable, a standard UUID implementation may already solve the problem. Choose Snowflake here because the assumed requirements call for compact 64-bit, roughly time-ordered IDs.

Interview decision: "If 128 bits are acceptable, I'd consider UUIDv7 to avoid worker-ID coordination. If compact 64-bit IDs are a requirement, I'd choose Snowflake and explicitly defend its failure handling. Neither guarantees strict global ordering or replaces authorization."

API and deployment choice

POST /ids returns {"id":"..."}. Bound batch size if batching is in scope. Define unavailable and timeout responses. A retry can generate a different unique ID; returning the same one needs a separate idempotency contract.

Baseline: a service. Clients call a load-balanced generator pool. A worker allocator grants durable, exclusive identities at assignment/recovery, not on every ID request. An embedded library avoids a network call per ID but gives each application instance the same identity and recovery responsibilities.

A stateless API over stateful generators

The API does not store generated IDs. Generators retain local sequencing state and durable recovery metadata.

Snowflake-style 64-bit layout

01 sign bit
Timestamp41 bits / milliseconds since custom epoch
Worker10 bits
Sequence12 bits
ID = ((currentMillis - customEpoch) << 22)
   | (workerId << 12)
   | sequence
FieldCapacityDesign implication
41-bit timeAbout 69.7 yearsChoose a fixed epoch and plan migration before timestamp exhaustion. Do not silently change the epoch inside the same namespace.
10-bit worker1,024 identitiesUnique active identity assignments; plan capacity and safe reuse. This is a shared namespace across regions unless region bits are explicitly reserved.
12-bit sequence4,096 IDs/ms/workerAbout 4.096M IDs/s/worker is the encoding ceiling, not a measured service capacity.

Why numeric sorting helps: timestamp bits are most significant. But clock skew can reorder events across workers; within one millisecond, worker bits influence sort order. Do not claim strict global creation order or gapless allocation.

Propose a design / normal request path

Explain the happy path before breaking it

First assume valid worker ownership, a clock that has not moved backward, and an available sequence number. The failure discussion below adds the guards needed for real operation.

Happy-path sketch

under a per-generator lock:
  now = read wall-clock milliseconds
  if now == lastTimestamp:
    sequence += 1
  else:
    sequence = 0
  lastTimestamp = now
  return pack(now - epoch, workerId, sequence)

Not production-ready pseudocode: this deliberately omits failure guards. Before emission, a complete implementation must verify ownership, clock and field bounds, sequence capacity, and durable recovery coverage.

Proof sketch

Different timestamps differ in the high bits. Within a timestamp, different worker IDs differ in the middle bits. Within one timestamp and worker, the serialized sequence is distinct.

Therefore collisions require a repeated tuple: (timestamp, worker ID, sequence). Clock rollback, unsafe ownership reuse, and restart-state loss are precisely the ways that repetition can occur.

A concrete example

At timestamp T, worker 17 emits sequence 0, then 1. Worker 18 may emit sequence 0 at the same time: its different worker bits keep the ID distinct.

Transition to the next discussion: "This works under those assumptions. Now let's examine what could repeat a tuple or prevent us from serving requests."

Stress the design / capacity and operational follow-ups

Scale it, observe it, and state its limits

QuestionYour answer
How do we scale?Add independently identified workers within the bit budget. Load-test actual capacity; avoid one network round trip per ID by embedding the generator where appropriate.
How do we detect problems?Track generation p99, sequence exhaustion waits, clock rollback, allocation failures, identity conflicts, and recovery waits. Sample/validate outputs, but do not rely on an after-the-fact duplicate check for correctness.
What should we test?Concurrent requests, frozen/backward clocks, restarts in the same millisecond, missing metadata, identity reuse, network partitions, sequence exhaustion, and epoch bounds.

Guarantee boundaries: IDs are approximately time-ordered, not gapless or strictly globally ordered. They are predictable: never use them as passwords, access tokens, or substitutes for authorization.

Interview closing: "I chose Snowflake-style IDs for compactness and approximate time ordering. The normal path is local generation. Uniqueness depends on exclusive worker identities, serialized sequence updates, and safe clock/restart handling. I would stop an unsafe generator rather than risk duplicates."

Active recall / expand after answering aloud

10 interview FAQs

1. Is a unique ID the same as a UUID?

No. UUID is a standardized 128-bit identifier format. A unique ID can also be a database sequence, range-allocated number, or custom 64-bit Snowflake-style value.

2. Can we guarantee that UUIDv4 never collides?

No. Its collision probability is extraordinarily small with a correct random source, but not zero. Snowflake's deterministic uniqueness is also conditional: ownership, time, sequence, and recovery rules must hold.

3. Why use a custom epoch?

Store elapsed milliseconds rather than milliseconds since 1970, leaving the full timestamp bit budget available from the chosen start date. All workers must use the same fixed epoch in one namespace.

4. Are Snowflake IDs globally ordered?

Only approximately by time. Clocks differ, concurrent requests have no single natural total order, and same-millisecond IDs sort partly by worker ID. Strict global ordering requires additional coordination or a stronger ordering service.

5. Why can't every server start with worker ID zero?

Two servers can use the same timestamp and sequence, yielding identical IDs. Worker allocation must guarantee distinct active identities, not merely make duplicates unlikely through hashing.

6. What happens after 4,096 IDs in one millisecond?

Wait for a later millisecond, recheck guards, then reset the sequence. Do not wrap the sequence inside the same timestamp. Use backpressure or fail the request if waiting exceeds the latency budget.

7. What if the machine restarts or loses its disk?

Restarting the same worker identity needs trustworthy recovery state and a timestamp beyond the reserved high-water bound. If that state is lost, quarantine the identity or establish safe reuse; do not silently reset it.

8. What if the allocator is unavailable?

Under the non-expiring exclusive-grant baseline, healthy owners with safe state can continue. New allocation and reassignment wait. A lease-based alternative must stop issuance before its valid ownership expires.

9. Should IDs be returned as JSON numbers?

Prefer strings for 64-bit IDs when JavaScript clients are possible. JavaScript Number represents integers exactly only up to 2^53 - 1. Use a true 64-bit integer representation internally.

10. Does retrying return the same ID?

Not by default: a generator retry can return a fresh unique ID. If the operation needs the same result on retry, persist an idempotency-key-to-ID mapping with its own atomicity, retention, and durability rules.
